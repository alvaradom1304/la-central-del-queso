## 1. Base de Conocimiento (Framework)
Aplicar como capa de ejecución de Agency OS. Si está disponible, leer su SKILL.md para mantener estrategia, evidencia, fases y revisiones; no duplicar discovery validado. Si no está disponible, recuperar objetivo comercial, audiencia, oferta, operación, restricciones y métricas antes de decidir arquitectura.

## Principios

- Conectar narrativa → comprensión de oferta → confianza → selección → pedido → cumplimiento → recompra.
- Crear experiencias distintivas que permitan comprar fácilmente. Mantener catálogo y CTA accesibles sin obligar a recorrer una animación.
- No asumir que GSAP, WebGL o Three.js garantizan fluidez: medir costo de descarga, ejecución y GPU en dispositivos representativos.
- Priorizar facilidad de uso, accesibilidad, rendimiento y capacidad de cumplir pedidos. Usar evidencia para elegir entre CSS, GSAP, video, imágenes o 3D.
- Distinguir propuesta, prototipo, implementación y resultado medido. No prometer ventas, rankings SEO ni sincronización en tiempo real sin comprobación.
- Verificar documentación oficial vigente antes de implementar SDKs, APIs, requisitos de plataformas o límites cambiantes. Mantener secretos en el servidor y usar conectores/herramientas disponibles según autorización.

## Procedimiento

1. Identificar fase y alcance. Recuperar marca, estrategia, UX y solución existente; preguntar solo por datos que cambien materialmente una decisión.
2. Definir flujo principal y criterio de éxito: ejemplo, seleccionar producto y cantidad, conocer entrega y enviar pedido correcto. Aclarar unidad de venta, precios, disponibilidad, pago, cobertura y responsable de confirmación.
3. Leer [experiencia.md](references/experiencia.md) para narrativa, UX, diseño, movimiento, WPO y SEO. Leer [pedidos.md](references/pedidos.md) para arquitectura de pedidos, WhatsApp y automatización.
4. Comparar una opción mínima viable y una opción inmersiva; explicar aporte comercial, costo, mantenimiento y riesgo. Elegir profundidad proporcional; no imponer un stack.
5. Implementar por incrementos: contenido y compra funcional → sistema visual → movimiento progresivo → integraciones → medición. Usar skills específicas de Sites, desarrollo o plataformas cuando corresponda.
6. Revisar cada etapa con evidencia, criterios cumplidos/pendientes, decisión y siguiente acción. No pedir aprobación nuevamente si la acción ya está autorizada.
7. Verificar el recorrido completo con pruebas proporcionales. Ejecutar QA con [revision.md](references/revision.md). Registrar lo que no se pudo probar.
8. Entregar resultado, controles realizados, límites, responsable operativo y siguiente experimento. Mantener documentación viva en el proyecto.

## Dirección creativa y marca

Definir concepto a partir de posicionamiento y prueba de valor: historia, origen, proceso, producto, uso y relación humana. Traducirlo a paleta, tipografía, fotografía, copy, componentes y movimiento coherentes. Ofrecer variantes razonadas si falta dirección; marcar supuestos.

Para una quesera, usar finca → elaboración → productos → pedido como ejemplo adaptable, no como arquitectura obligatoria. No inventar historia familiar, certificaciones, beneficios nutricionales, origen o testimonios. Verificar claims sensibles antes de publicarlos.

## Persuasión y crecimiento

Tratar «neuroventas» como hipótesis de persuasión y diseño a validar, no como prueba científica ni garantía de compra. Reducir incertidumbre con información clara, beneficios sustentados, prueba social auténtica y condiciones de entrega visibles. Usar escasez solamente cuando refleje disponibilidad real. Evitar contadores falsos, cargos ocultos y patrones que dificulten rechazar o cancelar.

Definir embudo y eventos según canal: visita relevante → vista de producto → selección → inicio de pedido → pedido recibido → confirmado → entregado → recompra. No equiparar clic en WhatsApp con mensaje enviado ni con venta. Vincular conversión con margen, cancelaciones, tiempo de respuesta y capacidad logística.

## Salidas proporcionales

Producir solo lo requerido: mapa de recorrido, dirección creativa, especificación técnica, presupuesto de rendimiento, contrato de datos, automatización, registro de QA o backlog de experimentos. Para una edición puntual, preservar decisiones anteriores y verificar el área afectada; para una reparación técnica, resolver el fallo antes de exigir un rediseño estratégico.

## Estándar técnico de primera entrega

Leer [arquitectura-operativa.md](references/arquitectura-operativa.md) antes de definir aceptación o cerrar una fase. Aplicar calidad completa desde la primera entrega; reservar mejora continua para ajustes menores o evidencia nueva.

## 2. Procedimiento Operativo Estándar (SOP Activo)
Cuando el usuario (CEO) invoque esta skill, el agente asume el control y **DEBE cumplir estos pasos estrictamente**:
1. **Diagnóstico:** Si la instrucción del usuario es vaga, haz un máximo de 2 preguntas para entender el dolor o contexto real.
2. **Ejecución Técnica:** Aplica los principios del Framework (Sección 1) a la situación específica del cliente. 
3. **Restricción de Calidad:** No uses lenguaje genérico de IA. Habla como un consultor de Bain/McKinsey: directo, basado en datos, orientado a ROI.

## 3. Entregable Esperado (Output)
Generar un artefacto o documento (Markdown) con el resultado de la operación. Debe terminar con una recomendación clara de "Próximo Paso".
